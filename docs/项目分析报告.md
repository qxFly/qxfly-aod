# 项目分析报告

**目标**：让 `cn.aodlyric.xiaowine`（酒域·息屏增强）适配 `com.miui.aod` DEV-2455.1.0.1-09282249，
并把歌词来源从 **Lyric-Getter** 换成 **SuperLyric**。

---

## 0. 结论速览

| 判断 | 结论 |
|---|---|
| `cn.aodlyric.xiaowine-main.zip` 是不是源码 | **不是**。它只是 Xposed-Modules-Repo 的发布元数据仓库（19 个文件，只有 README 和 10 张图） |
| 真正的源码在哪 | `SOURCE_URL` = `https://github.com/Wine-Network/AOD_For_MIUI`，**已 404，仓库不存在或已转私有** |
| 目标 APK 是什么 | `com.miui.aod`，「息屏与锁屏编辑」，versionCode 22455101 |
| 新版本是否还要自己画歌词 | **不需要**。新版内置了完整的 MAML 歌词通道，只认 `MediaMetadata` 的 `android.media.metadata.LYRIC` |
| 换 SuperLyric 难不难 | 接收端 API 很干净（`SuperLyric.receiver().register()`），难点在 **AccessPolicy 与隐藏 API** |
| 最大的坑 | 新版**没有任何** `Lyric_Data` / Lyric-Getter 广播接收器 —— 旧方案的"投稿口"已经没了 |

**一句话**：这是一个「**源码缺失的重建 + 架构降级**」工程 —— 因为新版 AOD 已经把歌词渲染做进 MAML 了，
模块的工作量可以从"自己画一个歌词视图"缩减为"往 MediaMetadata 里塞一段 LRC"。

## 1. 三份素材分别是什么

### 1.1 `cn.aodlyric.xiaowine-main.zip` —— 空壳发布仓库

这是 [Xposed-Modules-Repo](https://github.com/Xposed-Modules-Repo) 里**只有 Release、没有源码**的

> **⚠️ 这是本项目的第一个硬约束**：没有可分析的模块源码。
> 下文对旧模块的一切描述，都来自**反编译它已发布的 APK**（`AOD_Lyric-4.2.12.60.-release.apk`，3.5 MB）。

## 2. 新版本 AOD 的歌词链路（核心发现）

### 2.1 全仓库只有一条歌词通路

对三个 dex 做字符串扫描，`lyric` 相关符号**只出现在 `classes2.dex`**，且全部属于 MAML：

```
com/miui/maml/elements/MusicLyricParser
com/miui/maml/elements/MusicLyricParser$Lyric
com/miui/maml/elements/MusicLyricParser$LyricShot / LyricEntity / LyricHeader / EntityCompator
com/miui/maml/elements/MusicController
com/miui/maml/elements/MusicControlScreenElement
METADATA_KEY_LYRIC
android.media.metadata.LYRIC
.lyric_current / .lyric_before / .lyric_after / .lyric_last / .lyric_next / .lyric_prev
.lyric_current_line_progress
```

反编译后在 `sources` 里 grep `[Ll]yric`，命中文件只有两个（其余是 lottie / 云服务 multipart 的误伤）：

```
113  com/miui/maml/elements/MusicLyricParser.java
 66  com/miui/maml/elements/MusicControlScreenElement.java
```

**并且：`Lyric_Data`、`LyricData`、`SuperLyric`、`aodlyric`、`lyric.getter` 在所有 dex 中出现 0 次。**

> 结论：新版 AOD **完全不认识** Lyric-Getter 的广播协议。旧模块如果靠「AOD 里注册 `Lyric_Data`
> 接收器」取歌词，那条路在新版上必然断掉。

### 2.2 歌词从哪里进来

`com/miui/maml/elements/MusicControlScreenElement.java`：

```java
public static final String METADATA_KEY_LYRIC = "android.media.metadata.LYRIC";   // L37

// mMusicUpdateListener.onClientMetadataUpdate(MediaMetadata mediaMetadata):  L166
String string4 = mMetadata.getString(METADATA_KEY_LYRIC);                          // L201
MamlLog.d(LOG_TAG, "raw lyric: " + string4);
MusicLyricParser.Lyric parseLyric = MusicLyricParser.parseLyric(string4);         // L203
if (parseLyric != null) parseLyric.decorate();                                    // L205
if (parseLyric != null || z) { mLyric = parseLyric; updateLyric(parseLyric); }    // L207-210
requestFramerate(mLyric != null ? 30.0f : MAX_TEXTSIZE);                          // L212
```

上游是 `MusicController`（`MediaSessionManager.getActiveSessions()` + `MediaController.Callback`），
`onMetadataChanged` 直接把 `MediaMetadata` 抛给监听器。

### 2.3 歌词变量名

只有当 MAML 元素同时具备 `enableLyric="true"` 和 `name` 属性时才会创建（L323/L333-341）：

```xml
<MusicControl name="music" enableLyric="true" updateProgressInterval="1000">
```

对应变量：

| 变量 | 含义 |
|---|---|
| `@music.lyric_current` | 当前行 |
| `@music.lyric_before` | 当前行之前全部 |
| `@music.lyric_after` | 当前行之后全部 |
| `@music.lyric_last` / `.lyric_prev` | 上一行 |
| `@music.lyric_next` | 下一行 |
| `@music.lyric_current_line_progress` | 当前行进度 0~1 |

刷新由 `mUpdateProgressRunnable` 按 `updateProgressInterval`（默认 1000 ms）驱动，
位置取自 `mMusicController.getEstimatedMediaPosition()`，即 **系统 MediaSession 的 PlaybackState**。

### 2.4 LRC 解析器行为（写注入时要注意）

`MusicLyricParser.parseLyric(String)` 是 `static` 的，规则：

- 按 **`"\r\n"`** 切行（`CRLF` 常量）——**必须用 CRLF，用 \n 只会解析出一整行**；
- 每行 `[mm:ss.xx]文本`，`parseEntity` 用 `split(":")` 取秒数、前面各段按 60 进制累加；
- 支持头部 `[ti:]` `[ar:]` `[al:]` `[by:]` `[ve:]` `[offset:]`；
- 会先剥掉形如 `<0:00:00>` 的增强标签；时间必须 < 18000000 ms；
- 解析后按时间排序，并对重复时间戳做 `correctTime` 修正；
- `decorate()` 对每行执行 `Html.fromHtml(text + "<br/>")`。

## 3. 旧模块现在长什么样（反编译结论）

`cn.aodlyric.xiaowine` 4.2.12，单 dex，3.5 MB，**完全混淆**。

```
cn/aodlyric/xiaowine/hook/MainHook.java        ← 入口，111 行
cn/aodlyric/xiaowine/config/Config.java
cn/aodlyric/xiaowine/ui/...                    ← 设置界面
o0O.*                                          ← 真正的 Hook 逻辑全在这里（类名混淆）
```

结构（`MainHook.handleLoadPackage`）：

```java
if (!Config.getMainSwitch()) return;                       // 总开关
if (pkg.equals(S1)) { /* 跑 Hook 类 C0946o8 */ }           // 字符串运行时解密
if (pkg.equals(S2)) {
    if (Config.getLyricSwitch()) {
        // Hook Application 某个方法，注册为歌词入口
        XposedBridge.hookMethod(method, new oooO8oO8o(50, o00008o88));
    }
}
```

几个可直接读出的事实：

1. 模块用的是 **原生 Xposed API**（`de.robv.android.xposed.XposedBridge`），不是 libxposed。
2. 两个目标包名是 `AbstractC0906OO.m3128OO0(long)` 解密出来的常量，静态分析看不到明文。
3. 模块 **自带一套完整的歌词视图设计**：
   `lyricFontSize / lyricFontMaxWeight / lyricGradientColor / lyricStrokeWidth / lyricLetterSpacing /
   lyricGravity / lyricBackgroundRadius / lyricBackgroundMargins / lyricBackgroundGradientColor /
   lyricBlurredEdgesType / lyricViewIndex / whenLyricShow / whenLyricHide`
   —— 这些是新版 AOD **完全不提供**的能力，是新模块必须决定「保留还是废弃」的部分。
4. 依赖 `cn/lyric/getter/api/data/LyricData` 与 `ExtraData`，即直接吃 Lyric-Getter 的 Parcelable。

## 4. 两条歌词通道对比

### 4.1 现状：Lyric-Getter 广播

```
音乐App进程 ──Hook──> cn.lyric.getter 模块
                          │  sendBroadcast(Intent("Lyric_Data"))  +  LyricData(Parcelable)
                          ▼
                    com.miui.aod 进程 ──> 旧模块渲染
```

`LyricData` 结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | `OperateType` | `UPDATE` / `STOP` |
| `lyric` | String | **整首 LRC 文本** |
| `extraData` | `ExtraData` | `packageName`、`delay`、`customIcon`、`base64Icon`、`useOwnMusicController` |

特点：**跨进程广播 + 整首字符串**，无时间轴结构，进度靠 `delay` 推算，且**没有身份校验**
（同用户任意应用都能伪造）。

### 4.2 目标：SuperLyric Binder

```
音乐App进程 ──SuperLyric hook──> 采集歌词 ──Binder──> system_server
                                                        │ super_lyric.v4 / super_lyric
                                                        ▼
                                              com.miui.aod 进程（接收端）
```

接收端 API（`SuperLyricApi`）：

```java
SuperLyric.receiver().register(new LyricListener() {
    @Override public void onLyric(LyricView view) {
        Lyric doc      = view.getLyric();   // id / title / artist / album / duration / lines
        Line  cur      = view.getLine();    // text / start / end / words / translation / phonetic
        int   index    = view.getIndex();
        long  position = view.getPosition();
        float speed    = view.getSpeed();
        PlaybackState s= view.getState();
    }
    @Override public void onStop(Stop stop) { /* PAUSED/STOPPED/ERROR/PROCESS_DIED/CLEARED */ }
});
```

相比 Lyric-Getter 的三个实质提升：

| 维度 | Lyric-Getter | SuperLyric |
|---|---|---|
| 数据形态 | 整首 LRC 字符串 | 结构化 `Lyric{lines:[Line{start,end,text,translation,phonetic,words}]}` |
| 进度 | `delay` 推算 | 系统 MediaSession `PlaybackState`（`PlaybackClock`） |
| 访问控制 | 无 | `AccessPolicy` 按 UID 分级 |
| 逐字歌词 | 无 | 有（`Line.words`） |

## 5. 改造方案

### 5.1 推荐架构：把歌词喂进 `MediaMetadata`

新版 AOD 的渲染、排版、动效、逐行进度**全都是现成的**，唯一缺的是
`MediaMetadata.getString("android.media.metadata.LYRIC")` 返回空。
所以最省力、最稳的做法是**只补这一段数据**，让 MAML 自己跑完剩下 90%。

```
SuperLyric(系统) ──Binder──> [新模块·com.miui.aod 进程]
                                   │
                                   ├─ 1. SuperLyric.receiver().register(listener)
                                   ├─ 2. onLyric(view) → 记录当前曲目 + 生成整首 LRC
                                   └─ 3. Hook MediaMetadata#getString(String)
                                            key == "android.media.metadata.LYRIC"
                                            → 返回我们的 LRC
                                   ▼
                    MusicControlScreenElement.onClientMetadataUpdate()
                          → MusicLyricParser.parseLyric()
                          → @music.lyric_current / .lyric_before / ...
                          → 主题原生渲染 ✅
```

**为什么不再需要自己画歌词**：进度由 AOD 自己从 MediaSession 取，而 SuperLyric 的进度同源
（都来自系统 `PlaybackState`），天然对齐，不需要额外做时间同步。

### 5.2 三个可选注入点

| 方案 | Hook 点 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | `android.media.MediaMetadata#getString(String)`，按 key 过滤 | 1 个点；原生链路全复用；主题兼容性最好 | 需 Hook 框架类；必须精确按 key 过滤 |
| B | `com.miui.maml.elements.MusicLyricParser#parseLyric(String)` | 静态方法，最干净 | 要自己构造 `Lyric/LyricHeader/LyricEntity` 并处理 `decorate()` |
| C | `MusicControlScreenElement$1#onClientMetadataUpdate(MediaMetadata)` 之后反射写 `mLyric` 并调 `updateLyric()` | 最贴业务 | 依赖私有字段名，最脆弱 |

**方案 A 的 LRC 生成**（从 SuperLyric 的 `Lyric.lines` 反向拼）：

```java
StringBuilder sb = new StringBuilder();
for (Line line : doc.getLines()) {
    long ms  = line.getStart();
    long min = ms / 60000;
    long sec = (ms % 60000) / 1000;
    long cs  = (ms % 1000) / 10;
    sb.append('[')
      .append(String.format("%02d:%02d.%02d", min, sec, cs))
      .append(']')
      .append(line.getText())
      .append("\r\n");        // ← 必须是 CRLF
}
```

### 5.3 必须先解决的三件事

**(1) `AccessPolicy` —— com.miui.aod 拿得到 Binder 吗？**

`lyric-service/.../core/AccessPolicy.java`：

```java
public static Level resolve(boolean system, boolean supported, boolean marked, int versionCode) {
    if (system || supported) return Level.BOTH;     // 系统应用 / 受支持音乐应用 → 全开
    if (!marked) return Level.DENY;
    if (versionCode >= 40) return Level.V4;
    if (versionCode >= 31) return Level.LEGACY;
    return Level.DENY;
}
```

`com.miui.aod` 是系统应用，满足 `FLAG_SYSTEM | FLAG_UPDATED_SYSTEM_APP` → `Level.BOTH`，
**理论上可直接绑定**。但必须在真机上确认两点：

- 该 APK 是通过**覆盖系统应用**安装的（`FLAG_UPDATED_SYSTEM_APP`），而不是纯第三方安装；
- `SuperLyricSystemService` 的 `getCommonServicesLocked` 注入按 `attachApplicationLocked` 的 uid 生效，
  系统应用 UID 需要在白名单判定中被识别。

**注意**：`com.miui.aod` **不在** SuperLyric 的 `scope.list` 里，也不在 `SupportedApps.PACKAGES` 里 ——
它属于「借系统应用身份拿到 BOTH」这一类，不是被显式支持。

**(2) 隐藏 API：`android.os.ServiceManager`**

`SuperLyricApi` 的 `BinderHub` 通过 `ServiceManager.getService("super_lyric.v4")` 探测服务：

```kotlin
ServiceManager.getService(SERVICE_V4)?.let { binder -> V4Transport.probe(binder) }
```

这是隐藏 API。`com.miui.aod` 是普通应用进程（非 system），必须在模块里放开豁免，例如：

```java
// LSPosed 环境
XposedHelpers.setHiddenApiExemptions("Landroid/os/ServiceManager;");
// 或使用 HiddenApiBypass
```

这是**最容易在真机上翻车的一步**，建议第一版原型只做这一件事的连通性验证。

**(3) 主题必须开 `enableLyric`**

`mLyric*` 变量只在 `mHasName && mEnableLyric` 时才会创建。APK 内**没有** `.maml` 资源
（全在设备的主题包里），所以：

- 若用户当前息屏主题的 `<MusicControl>` 没写 `enableLyric="true"`，**歌词根本不会显示**；
- 这不是模块能绕过的 —— 除非退回「自己画视图」（即旧模块的做法）。

> 建议：模块设置页增加「主题兼容性检测」，读取当前主题 MAML 判断是否支持，
> 不支持时明确提示用户换主题，而不是让用户对着黑屏排障。

## 6. 风险与待验证项

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | 旧模块源码丢失 | 无法增量修改，只能重建 | 联系作者要源码；或按本文档重建（功能面已基本摸清） |
| 2 | 混淆严重（`o0O.*` + 字符串解密） | 无法直接读懂旧 Hook 点 | 需要 `AbstractC0906OO.m3128OO0(long)` 的解密算法还原 |
| 3 | `AccessPolicy` 判定失败 | 完全拿不到歌词 | 先做 Binder 连通性冒烟测试 |
| 4 | 隐藏 API 被拦 | `ServiceManager` 返回 null | `setHiddenApiExemptions` |
| 5 | 主题不支持 `enableLyric` | 歌词不显示 | 兼容性检测 + 文档引导 |
| 6 | SuperLyric 未覆盖某些音乐 App | 该 App 无歌词 | SuperLyric 支持 14 个 App，比 Lyric-Getter 少；需对齐用户常用 App |
| 7 | 锁屏编辑器在 `:keyguardeditor` 进程 | 若锁屏也要歌词，需要额外 scope | 确认需求边界，必要时加进程 scope |
| 8 | 新版 AOD 的 MAML 变量名可能随版本变动 | 升级即失效 | 变量名来自 `mName + ".lyric_*"`，相对稳定但需回归测试 |

**SuperLyric 支持的 App（对比旧方案）**：

Apple Music、波点、酷狗、酷狗概念版、酷我、酷我车机、咪咕、小米音乐、网易云、
Poweramp、QQ音乐、椒盐、汽水、Spotify、Flamingo、光锥、BreezyMusic

而 Lyric-Getter 覆盖面更广（含华为、魅族、Oppo、KDE Connect、MusicFree 等）。
**这是换源后的功能面收窄，需要跟用户确认可接受。**

## 7. 落地步骤建议

```
阶段 0  可行性冒烟（0.5 天）
        └─ 在 com.miui.aod 进程里跑通 SuperLyric.receiver().register()
           + 打日志确认能收到 onLyric()。这一步不通，后面全是空谈。

阶段 1  最小可用（1~2 天）
        └─ Hook MediaMetadata#getString → 返回拼好的 LRC
           + 用固定假数据先验证 MAML 变量能否刷新（排除主题因素）

阶段 2  接入真实数据（1 天）
        └─ SuperLyric onLyric → 曲目匹配（title/artist/duration）→ 生成 LRC
           + onStop 时清空

阶段 3  设置项迁移（1~2 天）
        └─ 决定旧模块那 15 个视图设置项的去留
           （MAML 主题不支持自定义字体/描边/渐变，只能废弃或另做兼容层）

阶段 4  主题兼容性检测 + 错误提示（0.5 天）

阶段 5  回归测试
        └─ 日志锚点：MamlLog 标签 MusicControlScreenE；SuperLyric 标签 SLDiag
```

**验证手段**：

```bash
adb logcat -s MusicControlScreenE MAML_MusicController   # 看 AOD 侧
adb logcat -s SLDiag SuperLyric                          # 看 SuperLyric 侧
# 关键日志："raw lyric: ..."  有内容 = 注入成功
```

## 8. 一句话总结

> 新版 `com.miui.aod` 已经把「息屏歌词」做成了系统能力，只是**没有数据源**；
> 模块的正确形态不再是「歌词渲染器」，而是「**歌词数据供给器**」：
> 用 SuperLyric 拿到结构化歌词 → 拼成 LRC → 塞进 `android.media.metadata.LYRIC` → MAML 自动渲染。
>
> 但这一切的前提是：**先确认 `com.miui.aod` 能通过 SuperLyric 的 `AccessPolicy`**，
> 以及**先把丢失的模块源码找回来或者接受重写**。
